# Rebuild on mutter virtual monitors — notes, 2026-11-11

Hardware: ThinkPad (Ryzen 5 7530U, Radeon "Barcelo", Mesa 25.2), GNOME Shell
46 / mutter 46.2 on Wayland; Galaxy Tab S7 FE (SM-T733, Snapdragon 778G,
2560×1600 @ 60 Hz, Android 14), USB 2.0 via adb.

## Measurements

Load: `bench/motion.py`, full-screen scrolling text on the tablet's monitor.

| | old (evdi → pipe → ffmpeg) | new |
|---|---|---|
| Frame rate under load | 44–46 fps | 60.0 fps |
| Frame rate the compositor could give the app | 45 fps | not limited by us |
| Frames dropped | — | 0 |
| Capture → tablet hands frame to display, p50 | not instrumented; 100–150 ms estimated in `phase5_log.md` | 36–41 ms |
| same, p95 | — | 50–57 ms |

"Capture → display" is measured by the tablet acknowledging each frame, so it
includes the trip back (~2–3 ms) and excludes the panel's own vsync wait and
scan-out (not measurable without a camera).

Where the 36–41 ms goes:

| Stage | ms | Notes |
|---|---|---|
| GPU colour conversion + encode | 11–12 | at the hardware's limit; 4.3 ms at 1280×800. The "quality" preset costs 29 ms. |
| Daemon relay | 0.1 | |
| adb link, each way | 1–3 | round trip 2.5 ms idle, ~6 ms under load |
| Tablet decode | 15–16 | floor ~10 ms regardless of resolution, codec, low-latency decoder, operating rate |

The tablet's decoder is the largest remaining piece and did not respond to
anything tried (H.264 vs HEVC, `…decoder.low_latency`, `KEY_LOW_LATENCY`,
Qualcomm vendor keys, frame rate 60, operating rate 120/240/32767,
1280×800 instead of 2560×1600).

## Why the old pipeline was slow

evdi has no GPU. For every frame mutter read the picture back into system
memory, pyevdi copied it out of the kernel, Python wrote 16 MB into a pipe,
ffmpeg read it and uploaded it to the GPU again. `write` alone was
12–14 ms/frame, and the back-pressure reached the compositor (45 fps).

## What replaced it

`org.gnome.Mutter.ScreenCast.RecordVirtual` creates a monitor whose frames are
dmabufs. `tdcap` imports each one into VAAPI, converts and encodes on the GPU.

## mutter 46 behaviours that had to be worked around

All found by measurement and then confirmed in mutter 46.2's source.

1. **dmabufs only with DRM modifiers.** A consumer that does not negotiate
   `SPA_FORMAT_VIDEO_modifier` gets shared-memory buffers filled by a CPU
   read-back: 39 fps. Ubuntu 24.04's GStreamer `pipewiresrc` (1.0.5) is such a
   consumer, which is why there is a C helper rather than a GStreamer pipeline.
   Prefer the implicit modifier over `LINEAR`.

2. **Virtual monitors repaint far too often.** Their frame clock has no vblank
   and never gets render-time measurements, so it falls back to "start
   rendering 87.5 % of an interval before the next presentation" from a
   presentation time of *now*: under continuous damage a nominal-60 Hz
   virtual monitor repaints every ~2.5 ms (~400 Hz). Apps that draw on frame
   callbacks follow. Not fixable from outside; a low nominal refresh rate
   (7.5 Hz → 60 real) tames it but is reported to apps as the refresh rate,
   which X11/Chromium-based apps would pace themselves by. Left at 60.

3. **The stream limiter drops frames.** Frames are limited by "time since the
   last buffer recorded" against the negotiated max framerate. At 60 that gave
   55 fps. In cursor-metadata mode a cursor-only buffer is recorded whenever
   *any* monitor prepares a frame, restarting the limiter: ~20 fps.
   Fix: the monitor's refresh rate is fixed when it is created and a later
   renegotiation of the same size keeps it, so `tdcap` negotiates 60, then
   renegotiates max framerate 1000 (limiter = 1 ms) and paces to a 60 Hz grid
   itself, always taking the newest frame. 240 was not enough (51 fps).

4. **Stale pointer images.** The software pointer overlay's "previous
   rectangle" is marked invalid by an update that does not move it, so the
   next move leaves the old image in the monitor's framebuffer. Seen where the
   pointer crosses onto/off the monitor and where it overhangs an edge, in
   both cursor modes, intermittently (roughly one run in three).
   Mitigation: `host/scrub.py` maps a transparent click-through X11 window
   over the monitor for 60 ms when the pointer enters or leaves, which makes
   mutter repaint it. **Not yet proven against a live reproduction**: it does
   produce a full repaint (frames appear at the map and unmap instants), but
   the bug did not recur in the three runs made after it was written, and one
   earlier run showed an edge sliver that survived a repaint.

5. **Virtual monitor serial numbers change per session**, so mutter's own
   `monitors.xml` never matches. The daemon stores and re-applies scale and
   position itself.

## Installed and verified (same day, later)

`./install.sh` run. Started by udev through the systemd user service: 60.0 fps
under load, 39.6 ms p50 / 56.9 ms p95. Cutting the USB port: service stopped
and monitor removed within 40 ms. Restoring it: display back, layout applied,
2.7 s later.

## Pointer overlay invisible (fixed same day)

Reported as "the cursor flickers, invisible most of the time". Two causes:

* **Android discarded it.** A window declares the area under a `SurfaceView`
  transparent, and the composer drops whatever the window draws there except
  inside the layout bounds of views that draw. The pointer view was moved by
  translation, so its bounds stayed in the top-left corner. The view
  hierarchy showed it visible and the window rendered a frame per move; the
  pixels were dropped at composition. What was visible now and then was the
  copy mutter bakes into a video frame when something else redraws while the
  pointer rests. Fix: a full-screen parent with `setWillNotDraw(false)`.
  Nudge-and-screenshot trials: 2 of 8 showed a pointer before, 8 of 8 after,
  each at the host's coordinates. 60.0 fps / 39.9 ms under load afterwards.
* **mutter sends the pointer image only when the shape changes**
  (`cursor_bitmap_invalid` starts false), never at stream start. The daemon
  now keeps the last image (also in `~/.cache/tabdisplay/pointer.bin`) and
  sends it to a new client first. Verified: reconnect with the pointer at
  rest, no image sent live, pointer drawn.

## Not done / open

* Stale pointer mitigation (item 4): six enter/rest-at-edge/leave cycles on
  the tablet with it active left nothing behind, where the same pattern
  without it left an image in roughly one run in three. Encouraging, not
  proof; no run has yet shown a stale image appear and then be removed.
* `--rc vbr/cbr` and its idle "refine" frames, and `--codec hevc` beyond one
  60 fps run, are lightly tested. Default is constant-QP 24: 5 Mbit/s for
  scrolling text; untested with video or photos, where the bitrate will be
  much higher.
* With the pointer overlay, a frame recorded while the pointer rests carries
  the pointer too; when it then moves, the old image stays for the ~40 ms the
  next frame takes.
* adb started this session wedged (`read failed: Protocol error`, later
  `can't set config #1, error -71`) and only a USB port power-cycle cleared
  it. Cause unknown. The udev rule tells ModemManager to leave the tablet
  alone, which is a guess at one contributor, not a confirmed fix.
* No touch or pen input.
* Tablet decode time (see table).
